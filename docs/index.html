Mark59 Parent Pom Repo

Purpose

This repository hosts Maven Parent POMs for Mark59-based UI scripting projects. By declaring one of these POMs as the <parent> in a consuming project, all common dependency versions, repository locations, and build plugin configuration are inherited automatically. This eliminates duplication and centralises maintenance across Mark59 script projects.

Links

  • GitHub Repository (source artefacts): https://github.com/mark59pom/parent-pom
  • Maven-structured repo (for inclusion in a pom.xml): https://mark59pom.github.io/parent-pom/

What Each Parent POM Provides

Inheriting from mark59-parent gives a consuming project:

  • Java 17 compiler source and target settings.
  • Centralised dependency versions managed via properties (JMeter, Mark59, Log4j 2, Jackson, Batik, DataFaker).
  • Pre-configured dependencies (all with provided scope where supplied by JMeter at runtime):
    • mark59-scripting (Selenium transitive dependency excluded, supporting Playwright-based scripts)
    • mark59-datahunter-api
    • ApacheJMeter_java
    • Log4j 2 (core, api, 1.2 bridge, SLF4J impl)
    • Jackson (core, databind, annotations) — added from 6.6.x; pinned to override transitive versions
    • Batik (multiple modules) — added from 6.6.x, provided scope
    • xstream — provided scope
    • datafaker (test data generation)
    • Additional dependencies may be added over time to mitigate vulnerabilities (should be indicated as such)
  • Build plugin configuration:
    • maven-compiler-plugin
    • maven-jar-plugin — produces a JAR with a classpath manifest pointing to a *-dependencies folder.
    • maven-dependency-plugin — copies all non-provided runtime dependencies into target/{artifactId}-dependencies/ at package time, ready for deployment into a JMeter lib/ext directory.
  • Repository declarations for resolving Mark59 artefacts:
    • From 6.6.0.01 onwards, all artefacts are sourced from Maven Central — no explicit repository declaration is needed in the consuming project.
    • Earlier versions (up to 6.6.0.00) declare https://mark-5-9.github.io/mark59-pages for Mark59 release artefacts and the Apache snapshots repository for JMeter SNAPSHOT builds.

Using a Parent POM in Your Project

Add the following <parent> block to your pom.xml, along with a repository entry so Maven can locate the parent POM itself before it is resolved: 

<parent>
    <groupId>mark59</groupId>
    <artifactId>mark59-parent</artifactId>
    <version>6.6.0.02</version>
    <relativePath />
</parent>

<repositories>
    <repository>
        <id>parent-pom-github</id>
        <url>https://mark59pom.github.io/parent-pom/</url>
        <releases>
            <checksumPolicy>ignore</checksumPolicy>
        </releases>
    </repository>
</repositories>

The consuming project then only needs to declare any additional dependencies specific to its own test scripts. All Mark59 and JMeter dependencies are already inherited.

Repository Structure

The Maven repository is served from the docs/ folder of the GitHub source repository via GitHub Pages. The directory layout follows the standard Maven 2 repository convention: 

docs/
  mark59/
    mark59-parent/
      maven-metadata.xml
      5.6.3.00/
      5.6.3.01/
      6.0.0.00/
      6.0.0.01/
      6.6.0.00/
      6.6.0.01/
      6.6.0.02/

Each version folder contains the .pom file for that release. No compiled JAR is published because a Parent POM has <packaging>pom</packaging>.

Updating a Published Parent POM

Maven treats a published release as immutable — once a version (e.g. 6.0.0.01) has been downloaded, Maven caches it in the local repository and will not re-fetch it, even if the file on the server changes. If you need to correct a published POM, choose one of the two options below.

Option 1 — Delete the cached POM (quick fix for the current machine)

When to use: you have already pushed a corrected POM to GitHub Pages under the same version number and you just need Maven to pick it up on the next build — on your own machine, or on a CI agent that has the stale entry.

Delete the cached version folder from the local Maven repository, then run your build normally. Maven will treat the artefact as missing and re-download it from GitHub Pages.

On Windows (PowerShell):

Remove-Item -Recurse -Force "$env:USERPROFILE\.m2\repository\mark59\mark59-parent\6.6.0.02"

On Linux / macOS:

rm -rf ~/.m2/repository/mark59/mark59-parent/6.6.0.02

Limitation: any other developer or build agent that already cached the old POM will also need to delete it manually. This approach does not scale beyond a single machine.

Option 2 — Increment the version number (recommended long-term practice)

When to use: the change is meaningful enough that consumers should be able to choose when to adopt it, or you want all developers and CI systems to pick it up automatically without manual cache-busting.

  1. Bump the version in the POM (e.g. 6.6.0.02 → 6.6.0.03).
  2. Publish the new version folder to docs/mark59/mark59-parent/6.6.0.03/.
  3. Update maven-metadata.xml to list the new version and set it as <release> / <latest>.
  4. Instruct consumers to update their <parent> version accordingly.

Because the new version has never been cached, Maven downloads it fresh on first use — no manual cache deletion is required on any machine.
